Objectives. By the end of this module I can:

1. What "systems operations" means

Systems operations is the work of keeping a running system healthy: deploying it, watching it, securing it, scaling it, fixing it, and controlling its cost. The developer builds the application. The operations person (often called a SysOps administrator or cloud operations engineer) makes sure it keeps running well. On AWS, much of this work is done with services and tools instead of racks and cables, so the course teaches you which service does which job.

3. Navigating the AWS Documentation website

The site is docs.aws.amazon.com. As a SysOps learner you will come back to it constantly, so learn its shape:

  • Search and service list. Find a service by name or browse by category (compute, storage, database, networking, management and governance).
  • Per-service documentation set. Each service has several guides. Typical ones: User Guide (how to use the service, concepts, console steps), API Reference (every API action and parameter), CLI Reference (every command for the AWS CLI), and sometimes a Developer Guide or Getting Started tutorial.
  • Left-hand table of contents. Use it to jump between concepts, tutorials, security, quotas and troubleshooting.
  • Other resources. Whitepapers and guides, SDKs and tools, and the "What's New" feed for updates. AWS re:Post and the Knowledge Center answer common operational questions.

AWS Identity and Access Management (IAM)

What it is. A free, global service that controls who can do what in an AWS account. It handles authentication (who are you?) and authorization (what may you do?). One IAM exists per account, so a user created once exists in every Region.

Regions. A Region is a separate geographic location made of several Availability Zones. The Region is where a resource runs, not where I am. I choose it for speed, legal compliance, cost, and service availability. Most services are regional; IAM is global.

Resources and ARNs. A resource is any object created in AWS (EC2 instance, S3 bucket, VPC, RDS database, IAM user...). Each has a unique ARN: arn:partition:service:region:account-id:resource. Global services such as IAM leave the Region empty, e.g. arn:aws:iam::123456789012:user/maria.

Building blocks. Root user (use once, protect with MFA), users, groups (hold users, carry policies), roles (temporary credentials), policies (JSON with Effect, Action, Resource), and MFA.

Workflow. Root creates a first admin and stops being used. The admin creates users, puts them in groups, and attaches policies to the groups. A user's permissions are the combination of all policies that apply to them.

Policy typeAttached toAnswers
Identity-basedUser, group, or roleWhat can this identity do?
Resource-basedA resource (e.g. S3 bucket)Who can access this resource?
Trust policyA role onlyWho can assume this role?

Three rules. Everything is denied by default. An explicit Deny always beats an Allow. Give least privilege: only what is needed.

Policy origins. AWS managed, customer managed, and inline. Prefer managed policies because they are reusable.

Corrections I made. IAM is global, not "available in all Regions". Region is about where the resource runs, not where I am. It is VPC (Virtual Private Cloud), not VPS. A trust policy is about assuming a role, not about a resource accepting actions.

Core CLI commands.

  • aws configure, aws sts get-caller-identity
  • aws iam create-user / list-users / get-user / delete-user
  • aws iam create-group / add-user-to-group / get-group
  • aws iam attach-group-policy / list-attached-group-policies / create-policy
  • aws iam create-role --assume-role-policy-document file://trust.json
  • aws iam attach-role-policy
