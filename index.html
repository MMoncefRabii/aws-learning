1. What "systems operations" means

Systems operations is the work of keeping a running system healthy: deploying it, watching it, securing it, scaling it, fixing it, and controlling its cost. The developer builds the application. The operations person (often called a SysOps administrator or cloud operations engineer) makes sure it keeps running well. On AWS, much of this work is done with services and tools instead of racks and cables, so the course teaches you which service does which job.

AWS Identity and Access Management (IAM)

What it is. A free, global service that controls who can do what in an AWS account. It handles authentication (who are you?) and authorization (what may you do?). One IAM exists per account, so a user created once exists in every Region.

Regions. A Region is a separate geographic location made of several Availability Zones. The Region is where a resource runs, not where I am. I choose it for speed, legal compliance, cost, and service availability. Most services are regional; IAM is global.

Resources and ARNs. A resource is any object created in AWS (EC2 instance, S3 bucket, VPC, RDS database, IAM user...). Each has a unique ARN: arn:partition:service:region:account-id:resource. Global services such as IAM leave the Region empty, e.g. arn:aws:iam::123456789012:user/maria.

Building blocks. Root user (use once, protect with MFA), users, groups (hold users, carry policies), roles (temporary credentials), policies (JSON with Effect, Action, Resource), and MFA.

Workflow. Root creates a first admin and stops being used. The admin creates users, puts them in groups, and attaches policies to the groups. A user's permissions are the combination of all policies that apply to them.

Policy typeAttached toAnswers
Identity-basedUser, group, or roleWhat can this identity do?
Resource-basedA resource (e.g. S3 bucket)Who can access this resource?
Trust policyA role onlyWho can assume this role?

Three rules. Everything is denied by default. An explicit Deny always beats an Allow. Give least privilege: only what is needed.

Policy origins. AWS managed, customer managed, and inline. Prefer managed policies because they are reusable.

Corrections I made. IAM is global, not "available in all Regions". Region is about where the resource runs, not where I am. It is VPC (Virtual Private Cloud), not VPS. A trust policy is about assuming a role, not about a resource accepting actions.

Core CLI commands.

  • aws configure, aws sts get-caller-identity
  • aws iam create-user / list-users / get-user / delete-user
  • aws iam create-group / add-user-to-group / get-group

  • aws iam create-role --assume-role-policy-document file://trust.json
  • aws iam attach-role-policy

1. The big idea: automate instead of click

You can manage AWS by clicking in the Console, but clicking does not scale: it is slow, hard to repeat, and mistakes sneak in. This module is about managing AWS with commands, scripts, templates and schedules. This idea is called infrastructure as code: the setup of your systems is written as text that a tool can run again and again with the same result.

2. AWS Systems Manager

Systems Manager is a service to manage many servers from one place, in AWS or on-premises. It can collect software inventory, apply OS patches, create system images and configure Windows and Linux. You choose the instances, define the task, and Systems Manager does it.

To be "managed", an instance needs three things. (1) The SSM Agent running on it, (2) an IAM role attached to it (an instance profile, for example with the managed policy AmazonSSMManagedInstanceCore), and (3) a network path to Systems Manager. This is the IAM role idea from Module 1 in action.

The big picture, animated

Features at a glance

FeatureWhat it doesRemember it as
Run CommandRemotely runs scripts or commands on many instances, with no bastion host and no SSH keys. IAM controls who can do it; CloudTrail records it."Remote control, one command, many servers"
Session ManagerInteractive browser-based shell to an instance. No inbound ports open, no bastion, no SSH keys, and the session is logged."Secure remote terminal"
Patch ManagerAutomates OS patching using a patch baseline and a maintenance window."Automatic updates, with rules"
Maintenance WindowsSchedules recurring tasks (such as patching) with limits on concurrency and error rate."A calendar for admin work"
State ManagerKeeps instances in a state you define (software installed, agents updated, settings applied), on a schedule."Keep servers the way I want them"
AutomationRuns multi-step workflows defined in an SSM document (restart unreachable instances, create golden AMIs, patch)."A recipe of steps"
Parameter StoreStores passwords, keys, license codes and database strings outside your code. IAM controls access and AWS KMS can encrypt them."A safe for secrets and settings"

Built-In InsightsA dashboard combining CloudTrail calls, AWS Config changes, inventory and patch compliance."One dashboard"

The workflows you must know

Patch Manager. The problems it solves: patching takes time, is repetitive, errors cause downtime, and compliance must be proven.
  1. Create a patch baseline (rules that approve or reject patches).
  2. Define a maintenance window and group instances into a patch group.
  3. Apply patches in the window and reboot every instance in the group.
  4. Review results and patch compliance.
Maintenance Windows.
  1. Create the window.
  2. Assign targets.
  3. Assign tasks: Run Command, Automation workflows, AWS Step Functions workflows, or AWS Lambda functions.
  4. Review task status afterwards.
State Manager.
  1. Create (or pick) an SSM document in JSON or YAML that defines the actions.
  2. Associate instances with the document and set a schedule.
  3. Optionally write the output to an Amazon S3 bucket.
Automation (build and test).
  1. Create an automation document or use a template (sequential steps and parameters).
  2. Run it (launch an instance, take a snapshot, tag, delete old images, terminate an instance).
  3. Monitor it, then confirm the result, for example by launching a test instance from the AMI it updated.
Parameter Store gotcha. SSM documents do not support references to SecureString parameters. To use a SecureString with Run Command, first retrieve the value, then pass it in. Naming note: the slides say Amazon CloudWatch Events can trigger automations. That service is now called Amazon EventBridge.

3. AWS Tools for PowerShell

A set of cmdlets (PowerShell commands, named Verb-Noun) to script AWS from PowerShell. They do the same jobs as the AWS CLI and support the same services and Regions as the AWS SDKs. Useful for quick tasks: security groups, launching instances, S3 buckets, IAM tasks, CloudWatch metrics.

4. SDKs and APIs

An API is how any program talks to an AWS service. An SDK (software development kit) wraps those APIs in a specific programming language so developers can use AWS inside their code without writing the low-level calls. The Console and the CLI use the same APIs underneath. This is what makes "infrastructure as code" possible. Each SDK comes with a getting started guide, developer guide, API reference and community forums.

5. AWS CloudFormation

You describe a whole infrastructure in one template (JSON or YAML). CloudFormation builds it as a stack, a group of resources managed as a single unit (EC2, RDS, VPC...). Create, update or delete the stack and all its resources follow.

  • Change preview: see what an update would change (does it delete or replace something critical?) before running it.
  • Drift detection: checks whether the real resources still match the template.
  • Custom extensions: use AWS Lambda for custom logic, such as looking up the newest AMI ID.

6. AWS OpsWorks

A configuration management service that provides managed Chef and Puppet, tools that configure servers using code, on EC2 or on-premises. Three offerings: OpsWorks for Chef Automate, OpsWorks for Puppet Enterprise, and OpsWorks Stacks. It automates infrastructure, application management, compliance testing and configuration tasks.

Note: AWS has been retiring OpsWorks offerings. Know it for the course, but check the current AWS docs before using it in a real project.

7. Hosting a static website on Amazon S3

A static website is made of pages with fixed content (plus optional client-side scripts) and no server-side processing. S3 can host one without any servers.

  1. Create a bucket.
  2. Enable website hosting on it, give the index document name (for example index.html) and allow public read of the content.
  3. Upload the site (Console or CLI), with a folder structure that matches the site.
  4. Open the endpoint URL: bucket-name.s3-website-region.amazonaws.com (dash) or bucket-name.s3-website.region.amazonaws.com (dot). The separator depends on the Region (Oregon uses a dash, Frankfurt a dot).

Custom domain. Use Amazon Route 53 to map your own domain. Create two buckets named exactly like the domain and the subdomain (mompopcafe.com and www.mompopcafe.com): one holds the content, the other redirects to it. Route 53 alias records point each name to its bucket endpoint.

New S3 buckets block public access by default, so to make the site public you must turn off Block Public Access for that bucket and add a bucket policy allowing reads. Only do that for website content.

2. User data and instance metadata

User dataInstance metadata
WhatA script or text you give the instance at launchFacts AWS knows about the instance (ID, hostname, subnet, IP...)
Used forBootstrapping: install and start software automaticallyLetting scripts discover details about themselves

User data is how Mom & Pop's deployment script becomes repeatable: every new instance builds itself the same way. The example from the slides installs a web server:

#!/bin/bash
yum update -y
service httpd start
chkconfig httpd on

Read it from outside with the CLI. The value is stored base64-encoded, so decode it to read it:

aws ec2 describe-instance-attribute --instance-id i-1234567890abcdef0 \
  --attribute userData --output text --query "UserData.Value" | base64 --decode

Without base64 --decode you see unreadable text starting with IyEvYmluL2Jhc2g..., which is the script encoded. Two more metadata examples from the slides (run them on the instance):

curl http://169.254.169.254/latest/meta-data/public-hostname
curl http://169.254.169.254/latest/meta-data/network/interfaces/macs/MAC/subnet-id
Good to know. (1) New instances usually require the safer IMDSv2, which first asks for a token: TOKEN=$(curl -X PUT "http://169.254.169.254/latest/api/token" -H "X-aws-ec2-metadata-token-ttl-seconds: 21600"), then curl -H "X-aws-ec2-metadata-token: $TOKEN" http://169.254.169.254/latest/meta-data/public-hostname. (2) Never put passwords in user data: anyone who can read it will see them. Use Parameter Store from Module 2.

3. Key pairs and logging in

EC2 uses public-key cryptography. Picture a padlock and its key: the public key is the padlock (AWS puts it on the instance), and the private key is the only key that opens it (you keep it). Together they are a key pair. You choose a key pair at launch, either creating a new one (download the private key then, because you won't get another chance) or using one you already have.

InstanceHow you log in
LinuxNo password by default. Connect with SSH using the private key.
WindowsUse the private key to decrypt the Administrator password, then connect with RDP.
aws ec2 create-key-pair --key-name my-key --query KeyMaterial --output text > my-key.pem
chmod 400 my-key.pem
ssh -i my-key.pem ec2-user@PUBLIC_DNS_NAME

# Windows: decrypt the Administrator password
aws ec2 get-password-data --instance-id i-0abc123 --priv-launch-key my-key.pem

Managing access for a whole fleet

The default Administrator or ec2-user is only a starting point. You must decide who gets access and how to remove it when people leave:

  • Windows: AWS Directory Service, to grant and revoke access using existing Windows users and groups.
  • Linux: Kerberos (a network authentication protocol, can be part of single sign-on), or your own key pairs made with ssh-keygen: put each user's public key in ~/.ssh/authorized_keys and give them the private key.
  • At scale: baking all users into an AMI is inflexible. Configuration management tools (Chef, Puppet, Ansible) add or remove access across many machines with a few commands.

Link to Module 2: Session Manager avoids the problem entirely, with no keys to hand out or revoke.

A user data script for it

On current Amazon Linux (2023), packages use dnf and services use systemctl (the slide's yum and chkconfig are the older style):

#!/bin/bash
dnf update -y
dnf install -y httpd php php-mysqli mariadb105-server
systemctl enable --now httpd
systemctl enable --now mariadb

Troubleshooting the script (checklist)

  • Read the log: /var/log/cloud-init-output.log on the instance.
  • Does the first line start with #!/bin/bash?
  • Are commands right for this OS (yum vs dnf, service vs systemctl)?
  • Does the script use -y? User data cannot answer prompts.
  • Can the instance reach the internet to download packages (public IP or NAT, route table, security group)?
  • Remember it runs only at first boot: after fixing it, launch a new instance to test.
  • Read the script back with describe-instance-attribute to confirm what was really passed.

What I learned

User data vs metadata

User data is what I tell the instance to do: a script that installs and configures software. It runs only at first boot, as root. To test a fixed script I must launch a new instance. Never put secrets in user data. Newer instances usually require IMDSv2 (token) for metadata.

Key pairs and access

A key pair has a public key (on the instance, placed by AWS) and a private key (kept by me). It proves who I am when I log in; it does not encrypt data at rest. Linux: SSH with the private key. Windows: decrypt the Administrator password with the private key, then RDP.

Fleet access. Baking users into an AMI is inflexible. When someone leaves, their public key must be removed from every instance. Better: Directory Service (Windows), Kerberos, or configuration management (Chef, Puppet, Ansible). Best here: Session Manager (Module 2), where IAM permissions control access and there are no keys. IAM roles control AWS API access, not the OS inside the instance by themselves.

2. Elastic Load Balancing (ELB)

A load balancer is the single point of contact for clients and distributes traffic across multiple targets (EC2 instances, containers, IP addresses), in one or several Availability Zones. You configure it in the EC2 section of the Console, with the AWS CLI, or with the SDKs.

TypeLayerBest for
Application Load Balancer (ALB)7 (application)HTTP/HTTPS, content-based routing, containers, microservices, WebSocket and HTTP/2. Recommended for most VPC use cases.
Network Load Balancer (NLB)4 (transport)TCP/UDP, tens of millions of requests per second, ultra-low latency, sudden traffic spikes, one static IP per Availability Zone.
Classic Load Balancer (CLB)4 and 7Basic balancing, for applications built in the old EC2-Classic network. Legacy.

Added by me: AWS also offers a Gateway Load Balancer, for virtual network appliances such as firewalls. It is not in the slides you pasted.

Key features

  • High availability: traffic goes to targets in one or several AZs.
  • Health checks: unhealthy targets stop receiving traffic; the load spreads over the healthy ones.
  • Security: security groups on the load balancer, and optional internal (non-internet-facing) load balancers.
  • TLS termination: the load balancer decrypts HTTPS, with integrated certificate management, so your servers save CPU.
  • Layer 4 or layer 7: pure TCP, or HTTP/HTTPS features.
  • Monitoring: CloudWatch metrics and request tracing.

The four ALB building blocks

PieceMeaning
ListenerA process that checks for connection requests, using the protocol and port you set (for example HTTP on 80). A load balancer can have several.
RuleBelongs to a listener. Each rule has a condition, a priority and an action (forward to a target group). Every listener must have a default rule.
Target groupA set of targets (EC2 instances, ECS container instances) that receive requests on a protocol and port. A target can be in more than one target group.
Health checkConfigured per target group and run on all its registered targets.

Content-based routing example: www.example.com/orders goes to one group of instances, /images to another, and the registration area to a third.

3. Amazon EC2 Auto Scaling

It keeps your application available by adding or removing instances automatically. It has three parts:

  1. Launch configuration or launch template: what to launch: IAM role, security groups, storage, instance type, user data, key pair (and the AMI).
  2. Auto Scaling group (ASG): where and how many: minimum, maximum and desired size, across subnets or AZs.
  3. Scaling policies: when to add or remove.

Note: the slides say "launch configuration". AWS now recommends launch templates, which are newer and replace launch configurations. The concept is the same.

Ways to scale

MethodHow it works
Health-based (steady-state group)Min = max = desired = 1, so one instance is always running. If it is marked unhealthy (a failed check, or aws autoscaling set-instance-health), the group terminates it and launches a new one. For a NAT instance this is still a single point of failure, with downtime during replacement.
ScheduledFor predictable load (traffic rises Wednesday, falls Friday). A scheduled action sets new min, max and desired values at a given time.
Dynamic, target trackingYou pick a metric and a target (like a thermostat) and Auto Scaling does the rest.
Dynamic, step scalingAdjustments vary with how far the alarm is breached. No cooldown periods for step policies.
Dynamic, simple scalingOne scaling adjustment per alarm.
PredictiveMachine learning forecasts traffic from daily and weekly patterns (needs at least 1 day of history, re-evaluated every 24 hours, forecasts the next 48 hours) and schedules capacity ahead of time. Good for cyclic traffic, not for random spikes. It can be combined with dynamic scaling.

Rule of thumb. If the metric rises and falls proportionally with the number of instances (such as average CPU), use target tracking. Otherwise use step scaling. Scaling can be driven by instance health, CloudWatch alarms, a time schedule, or past usage.

4. Amazon Route 53

Route 53 is AWS's DNS service. It registers or transfers domain names, resolves names to IP addresses, and can route traffic to resources in different Regions or on-premises. An ELB gets a default DNS name, or you can use your own domain through Route 53.

RecordWhat it does
CNAMERedirects a name to any other DNS name (for example apex.example.com to acme.example.org).
AliasRedirects only to selected AWS resources (S3 website bucket, CloudFront distribution, load balancer, or another record in the same hosted zone).

Added by me: an alias record can be used at the zone apex (example.com itself), where a CNAME cannot, and Route 53 does not charge for alias queries to AWS resources.

The 7 routing policies

PolicyUse it when...
SimpleOne resource does the job (one web server for example.com)
WeightedYou want to split traffic in proportions (90% / 10%)
LatencyYou have resources in several Regions and want the lowest latency
FailoverYou want active-passive failover
GeolocationRouting by where the users are
GeoproximityRouting by where the resources are, with optional shifting of traffic
Multivalue answerRoute 53 answers DNS queries with up to eight healthy records, chosen at random

Latency-based routing (LBR). With load balancers in Oregon and Sydney, Route 53 uses its latency data to send a user in Barcelona to the Region that answers fastest. Usually that is the closest one, but not always.

Blue/green deployment. Run two matching environments, each with its own load balancer and Auto Scaling group: blue (current) and green (new). Use weighted routing to shift users gradually from blue to green, monitor green with CloudWatch and CloudWatch Logs, and shift back to blue if there are problems. Once green is stable, retire blue. Because of DNS caching, shutting down blue fully can take from a day to a week.

Load testing. Simulate traffic with open source tools before going to production, to confirm the scaling design works.

6. AWS Step Functions

Coordinates multiple AWS services into serverless workflows, for example combining Lambda and ECS. A workflow is a series of steps, and the output of one step is the input of the next.

  • You express it as a state machine. The console draws it graphically, easy to understand, explain and change.
  • A state can do work (a Task), or choose a branch (a Choice). Tasks call code hosted in a function, container or instance, and can run for up to 1 year.
  • Step Functions triggers and tracks each step, lets you monitor each one as it happens, and retries on errors so the application runs in order.
  • You can change, add or delete tasks and step order without changing code.
{"StartAt":"Validate","States":{
  "Validate":{"Type":"Task","Resource":"arn:aws:lambda:...:function:validate",
              "Retry":[{"ErrorEquals":["States.ALL"],"MaxAttempts":3}],"Next":"Paid"},

  "Prepare":{"Type":"Task","Resource":"arn:aws:lambda:...:function:prepare","End":true},
  "Reject":{"Type":"Fail"}}}
aws stepfunctions create-state-machine --name cafe-order --definition file://def.json \
  --role-arn arn:aws:iam::123456789012:role/sfn-role
aws stepfunctions start-execution --state-machine-arn SM_ARN --input '{"paid":true}'
